## 2. Logic Chain
1. **R1 requirement** states that the ML pipeline must forecast route traversal times based on future timestamps, and backend verification requires a `POST /api/v1/predict` endpoint.
2. Based on the observation of `backend/app.py` and `backend/graph_manager.py`, the routing is currently static and doesn't handle time-dependent traffic weights.
3. To compute predictive routing, we must snap start/end coordinates to the graph nodes, find the shortest distance route, and extract path features (distance, midpoint, time of day, day of week, weather, city).
4. Predicting a dimensionless congestion multiplier ($T_{actual}/T_{base}$) rather than raw seconds will normalize travel times across arbitrary route distances.
5. In **R3**, architectural strictness demands that the ML and simulation code remain separate from graph routing. The LLD design solves this by declaring abstract interfaces (`ITrafficModel` and `IPredictionEngine`) and decoupling model evaluation from routing query logic.

## 3. Caveats
* We did not compile the C++ `georoute_core` extension, as it was out of scope for a read-only investigation.
* We assumed that historical training data will be generated by the simulator script prior to training the real ML models.
* We did not test real scikit-learn models on local hardware, only designed the pipeline and classes.

## 4. Conclusion
The GeoRoute project needs to implement three python files to support predictive routing:
1. `backend/data_simulator.py` (traffic pattern generator).
2. `backend/train_model.py` (scikit-learn training pipeline).
3. `backend/prediction_engine.py` (OOP predictor wrapping model & feature engineering).
FastAPI (`app.py`) needs to load this engine and offer `/api/v1/predict` and `/api/v1/predict/traffic-density` endpoints.
